<objective>
The schema-changing plan. Three migrations land here, gated by a [BLOCKING] prisma migrate task that must run AFTER all schema edits and BEFORE verification (TypeScript checks pass without a live migration because Prisma types come from the generator, not the database — a forgotten migrate is the classic false-green failure mode).

Migration 1 (20260607000000): structural prep — BookTransaction.extended Boolean column + data backfill (penaltyDays=-1 rows become extended=true, penaltyDays=0); Book.availableCount CHECK constraint (>= 0).
Migration 2 (20260607000001): new BookTransfer model + capture the orphan Phase-1 composite index @@index([userId, calculatedAt]) on ReadingIndex so the partition migration can rely on it being declarative.
Migration 3 (20260607000002): convert ReadingIndex from heap to PARTITION BY RANGE (calculatedAt) — raw SQL because Prisma cannot generate this — and ATTACH 16 monthly partitions (prior 13 months + current + next 2 months as margin). This MUST be a hand-edited raw migration; `prisma migrate dev` cannot generate it.

Then the service-layer hardening: convert the four remaining array-form $transaction([...]) call-sites to interactive callback form (BOOK-05 service half); refactor returnRoaming to create a BookTransfer{status: PENDING} instead of bumping the source library's availableCount (BOOK-02 service half — confirm endpoint lands in Plan 02-05); replace the penaltyDays=-1 magic number in extendDueDate with the new extended Boolean.

Purpose: This is the load-bearing structural plan. Without RI-05 partitioning the ReadingIndex table becomes a query-planner casualty at 5M users × 30 days. Without the CHECK constraint, BOOK-05's interactive transactions still cannot reject a race-loser at the DB layer. Without the BookTransfer model, every roaming return corrupts the source library's inventory the moment the book physically leaves it.

Output: A migrate-clean Prisma state where the live DB reflects every schema declaration, the partition-detach cron (Plan 02-04) has partitions to manage, the confirm-transfer endpoint (Plan 02-05) has a model to write to, and the RI batch (Plan 02-03) reads from a query-planner-friendly table.
</objective>
