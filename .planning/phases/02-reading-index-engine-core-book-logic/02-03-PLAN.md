<objective>
The load-bearing decision of Phase 2. Replace the sequential nightly RI loop (projected ~69 hours at 5M users) with BullMQ fan-out reading from the Phase-1-provisioned read replica and writing to the Plan-02-02-partitioned ReadingIndex table.

Three artifacts land here: PrismaReplicaService (a second PrismaClient pointing at DATABASE_REPLICA_URL with graceful fallback when the env var is unset, matching the Phase 1 KafkaConsumerService graceful-no-op pattern), RiRecalcProcessor (WorkerHost with concurrency 10 that processes one 1000-user chunk per job), and the rewritten ReadingService cron handler that fans out N chunks via Queue.addBulk in a single Redis round-trip.

The reading-speed Trust Score signal (FRAUD-05) is computed in the same processor pass — when a chunk's transactions are loaded, the processor walks the BookTransaction rows and applies the trust-score delta for impossibly-fast (pages/hour > 100) or implausibly-quick (borrow-to-return < 30min) reads. Trust score writes happen in a single updateMany per chunk against the primary.

Purpose: This is the architectural fix for the C6 critical pitfall (sequential nightly cron). At 5M users / 1000 per chunk = 5000 jobs × ~12 sec / job × 10 concurrent ≈ 100 minutes wall-clock — well under the 2h target. Plan 02-02 already shipped the partitioned table; this plan makes inserts cheap because PG routes by partition key.

Output: A nightly RI batch that scales linearly with replica capacity, leaves the primary DB free during the batch window, and folds the reading-speed Trust Score signal into the same pass.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BullMQ queue (Redis) → worker | Job payloads (chunkIndex, offset, limit, scheduledAt); attacker who can write to Redis can flood the queue — defended by Redis ACL (Phase 1 INFRA-01 baseline) + idempotency keys |
| RiRecalcProcessor → DATABASE_REPLICA_URL | Read-only role; defended by replica being a streaming standby with no write capability; failed read does not corrupt primary |
| RiRecalcProcessor → DATABASE_URL (primary) | Bulk writes via createMany; defended by partitioned table + composite PK including calculatedAt routes inserts safely |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-12 | Denial of Service | Job flooding RI_RECALC_QUEUE | mitigate | jobId derived from `ri-recalc:${scheduledDate}:${chunkIndex}` (BullMQ dedupes by jobId); only the cron can enqueue (no public endpoint); removeOnComplete: 100 caps memory growth (ASVS V11.1.4) |
| T-02-13 | Tampering | Duplicate ReadingIndex rows from retried jobs | mitigate | jobId uniqueness + idempotent processor: the chunk's range (offset, limit) deterministically maps to userIds; createMany failure on retry would surface a Prisma error caught and the processor MUST delete-then-insert for that chunk's date+userIds before re-attempting createMany (research Risk 2) |
| T-02-14 | Information Disclosure | Replica lag exposes slightly-stale data | accept | Daily-granularity statistic tolerates seconds-to-minutes lag; documented in research Open Q 5 |
| T-02-15 | Spoofing | Worker pulls from a tampered Redis | accept | Phase 1 INFRA-01 already gates Redis access via cache.service security perimeter; no Phase 2 change needed |
| T-02-16 | Tampering | Trust score reading-speed signal gamed by users leaving books closed | mitigate | Two-sided gate: pages/hour > 100 OR borrow-to-return < 30min triggers -5; pages/hour in plausible range causes no change (no false positive for slow readers); spec asserts both directions (ASVS V11.1.7) |
</threat_model>
