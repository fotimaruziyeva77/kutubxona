<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP POST /books/import → backend | Untrusted multipart XLSX (potentially huge, potentially malformed); defended by FileInterceptor max 10MB + exceljs streaming parser + job-queue isolation |
| HTTP GET /ai/fraud/review-queue → admin caller | Sensitive PII (flagged users); defended by JwtAuthGuard + RolesGuard(SUPER_ADMIN, TUMAN_ADMIN, VILOYAT_ADMIN) |
| HTTP POST /ai/fraud/:userId/resolve → admin caller | Mutation of a user's review status; defended by RolesGuard + audit log entry written for every resolution |
| fraud.detected Kafka emit | Outbound to consumers; payload contains userId + riskScore but NO PII; consumers downstream are trusted |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-17 | Denial of Service | XLSX bomb (zip-bomb-style or formula-recursion exhaustion via exceljs) | mitigate | exceljs streaming reader + 10MB upload cap + BullMQ job isolation (worker crash != API crash); attempts: 2 with no retry on parse failure (the file won't suddenly become valid) (ASVS V12.1.1) |
| T-02-18 | Elevation of Privilege | Non-admin caller hits /ai/fraud/review-queue | mitigate | @UseGuards(JwtAuthGuard, RolesGuard) + @Roles(SUPER_ADMIN, TUMAN_ADMIN, VILOYAT_ADMIN); tested with role-scoped spec cases (ASVS V4.1.1) |
| T-02-19 | Information Disclosure | review-queue exposes user PII to lower-tier admins | mitigate | TUMAN_ADMIN sees only users in their tuman (Address.tumanId scoping); VILOYAT_ADMIN sees only their viloyat; SUPER_ADMIN sees all; scoping enforced by the service-layer where clause (ASVS V4.2.1) |
| T-02-20 | Tampering | dailyFraudScan auto-block removed but fraud.service.spec must still assert no user.update call survives | mitigate | spec asserts `prisma.user.update` is NEVER called in the dailyFraudScan path; spec is the canary for accidental re-introduction (ASVS V11.1.5) |
| T-02-21 | Tampering | Late confirmStorePurchase past 24h | mitigate | server-side `if (now - isbnScan.createdAt > 24h) throw BadRequestException` — clock-skew-tolerant because the check is server-vs-server-time, not client time (ASVS V11.1.4) |
| T-02-22 | Tampering | Partition-detach cron drops too much (off-by-one month boundary) | mitigate | spec asserts the cron computes the cutoff as `date_trunc('month', CURRENT_DATE) - INTERVAL '13 months'` (exactly 13 months ago, month-aligned); drops only that partition (ASVS V8.3.5) |
</threat_model>
